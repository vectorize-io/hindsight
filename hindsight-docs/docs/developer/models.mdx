# Models

Hindsight uses four kinds of model. Only the LLM needs setting up: the embedding model and the reranker run locally by default, and the decision model is optional.

| Model | What it does | Default |
|---|---|---|
| [**LLM**](#llm) | Extracts facts on retain, consolidates observations, writes reflect answers and knowledge pages | `openai` provider, `gpt-4o-mini` |
| [**Embedding model**](#embedding-model) | Turns text into vectors for semantic search | `BAAI/bge-small-en-v1.5`, local |
| [**Reranker**](#cross-encoder-reranker) | Orders recall candidates by relevance | `hindsight-ai/hs-rerank-1`, local |
| [**Decision model**](#decision-model) | Answers quick typed judgments so recall, consolidation, reflect and knowledge pages skip LLM calls | Off. See [Decision Models](./decision-models) |

Local models download from Hugging Face on first run. Every setting is listed in [Configuration](./configuration#llm-provider); this page covers what each provider needs.

## LLM

Used for fact extraction, entity resolution, observation consolidation and answer synthesis. Pick a provider: its card shows the default model, so setting the model is optional.

Every provider is set the same way, with `HINDSIGHT_API_LLM_PROVIDER` and, for most, `HINDSIGHT_API_LLM_API_KEY`. The same applies per operation: `HINDSIGHT_API_RETAIN_LLM_PROVIDER=anthropic` gives retain its own provider at that provider's default model. See [Per-Operation LLM Configuration](./configuration#per-operation-llm-configuration).

### Provider Capabilities

Some providers support features that lower cost or latency. Hindsight uses each one automatically when the configured provider supports it; the provider's card in the grid above shows which:

- **Batch API**: submits bulk retain extraction through the provider's asynchronous batch endpoint, typically at about 50% lower cost. When it isn't available, calls run synchronously.
- **Prompt caching**: reuses the large fixed system prefix that retain and consolidation send on every call, billed at the provider's cached-input rate. On Gemini and Vertex AI this uses the `CachedContent` API. On by default; turn it off with `HINDSIGHT_API_LLM_PROMPT_CACHE_ENABLED=false`. The cached prefix is the same for every bank, so one cache serves them all, and a failed cache creation falls back to an uncached call.

:::note
A card without "Prompt caching" does not mean a provider has no caching. OpenAI caches a stable prompt prefix automatically on its side, with no configuration. The badge tracks only Hindsight’s explicit caching hook, which Gemini and Vertex AI implement today.
:::

### Model requirements

- **Follows a JSON schema.** Every call, reflect's tool calls included, is a reply to a response schema (structured output); native tool calling is not used, so the model needs no tool support.
- **At least 65,000 output tokens.** Retain asks for long structured output. For a model with a smaller output limit, lower `HINDSIGHT_API_RETAIN_MAX_COMPLETION_TOKENS` (for example to `32000` or `16000`). It must stay above `HINDSIGHT_API_RETAIN_CHUNK_SIZE` (default `3000`); the server checks this on startup.
- **Thinking models share the output budget with their reasoning.** On Gemini 2.5+/3.x, GPT-5 and o-series, Grok reasoning and Claude extended thinking, the provider's output cap covers reasoning plus the visible answer, so a small cap can be used up by reasoning and leave the answer cut off. Reflect's synthesis call is uncapped by default for that reason; `HINDSIGHT_API_REFLECT_MAX_COMPLETION_TOKENS` sets a hard ceiling, so leave room for reasoning above your page length. A Gemini call that hits its cap logs a `truncated at max_output_tokens` warning instead of returning half an answer.

The LLM is the main bottleneck for retain. See [Performance](./performance) for ways to speed it up.

### Cheap Memory Model with Failover

Hindsight calls its own LLM, with its own credentials, only to process memory: extracting facts on retain, consolidating observations, refreshing mental models, and answering reflect. Your agent keeps calling whatever model it already uses. So the memory model can be a cheap, high-throughput one, picked for volume rather than for the agent's reasoning.

A typical production setup puts the cheap model first and stronger, pricier models behind it, used only when the cheap one fails. The building blocks are documented in [Multi-LLM Strategies](./configuration#multi-llm-strategies-failover--round-robin) and [Per-Operation LLM Configuration](./configuration#per-operation-llm-configuration):

```bash
# Member 0 (primary): cheap workhorse, serves almost every call
export HINDSIGHT_API_LLM_PROVIDER=groq
export HINDSIGHT_API_LLM_API_KEY=<groq-key>
export HINDSIGHT_API_LLM_MODEL=<cheap-model>

# Member 1: mid-tier fallback
export HINDSIGHT_API_LLM_1_PROVIDER=openai
export HINDSIGHT_API_LLM_1_API_KEY=<openai-key>
export HINDSIGHT_API_LLM_1_MODEL=<mid-model>

# Member 2: top-tier last resort, with its own retry budget
export HINDSIGHT_API_LLM_2_PROVIDER=anthropic
export HINDSIGHT_API_LLM_2_API_KEY=<anthropic-key>
export HINDSIGHT_API_LLM_2_MODEL=<top-model>
export HINDSIGHT_API_LLM_2_MAX_RETRIES=3

export HINDSIGHT_API_LLM_MAX_RETRIES=0   # fail over at once instead of retrying the same member
export HINDSIGHT_API_LLM_STRATEGY='{"mode": "failover"}'
# Or spread load instead: '{"mode": "round-robin", "weights": [4, 1, 1]}'
```

To give one operation a stronger model, override only that operation's primary. Its chain still falls back to the global members above:

```bash
# Consolidation starts on the mid-tier model; retain and reflect stay on the cheap one
export HINDSIGHT_API_CONSOLIDATION_LLM_PROVIDER=openai
export HINDSIGHT_API_CONSOLIDATION_LLM_API_KEY=<openai-key>
export HINDSIGHT_API_CONSOLIDATION_LLM_MODEL=<mid-model>
```

Give an operation a fully separate chain with its own indexed members and strategy (`HINDSIGHT_API_RETAIN_LLM_1_PROVIDER`, `HINDSIGHT_API_RETAIN_LLM_STRATEGY`, ...).

Things to know:

- **Number members from 1 with no gaps.** Hindsight stops reading at the first missing `HINDSIGHT_API_LLM_<n>_PROVIDER`: with `_1_` and `_3_` set, member 3 is ignored.
- **An operation with no members or no strategy of its own uses the global ones.** Mental-model refresh uses the reflect chain first, then the global one.
- **Batch retain does not fail over.** With `HINDSIGHT_API_RETAIN_BATCH_ENABLED=true`, the whole batch runs on the first member whose provider has a batch API. Put a reliable provider there.
- **Startup sends a test call to each configured model.** A model that is down only logs a warning; the server still starts. Set `HINDSIGHT_API_SKIP_LLM_VERIFICATION=true` to skip these checks, for example when fallbacks are paid per call or slow to answer.

### OpenRouter {#llm-openrouter}

Any model slug OpenRouter serves.

<ProviderSetup>

```bash
export HINDSIGHT_API_LLM_PROVIDER=openrouter
export HINDSIGHT_API_LLM_API_KEY=your-api-key
# export HINDSIGHT_API_LLM_MODEL=qwen/qwen3.5-9b   # the default
```

</ProviderSetup>

OpenRouter can serve one model from several hosts. A model slug like `z-ai/glm-5.3-flash` names who made the model, not the host your request lands on. On every call that asks for JSON back (fact extraction, consolidation, reflect's tool calls), Hindsight sets `provider.require_parameters=true`, so OpenRouter only picks hosts that support every parameter sent.

To pick the hosts yourself, set OpenRouter's [provider routing](https://openrouter.ai/docs/features/provider-routing) keys. Your `provider` keys are kept and win over Hindsight's:

```bash
export HINDSIGHT_API_LLM_EXTRA_BODY='{"provider":{"only":["deepinfra","novita"],"allow_fallbacks":false}}'
```

If a model fails with "No endpoints found that can handle the requested parameters", no host supports every parameter sent. Models that reject `temperature` are the usual cause. Set `HINDSIGHT_API_LLM_TEMPERATURE=none` to stop sending it.

### GitHub Copilot Setup

Use a GitHub Copilot subscription for Hindsight's extraction, consolidation, and reflection calls through the official GitHub Copilot SDK.

<ProviderSetup>

**Prerequisites:**
- An active GitHub Copilot entitlement
- Copilot CLI signed in under the same operating-system user that runs Hindsight

**Configure Hindsight:**

```bash
export HINDSIGHT_API_LLM_PROVIDER=github-copilot
export HINDSIGHT_API_LLM_MODEL=gpt-5.6-terra
# No HINDSIGHT_API_LLM_API_KEY is needed.
```

The provider starts one shared Copilot runtime for all Hindsight LLM lanes. That runtime uses a hook-free temporary `COPILOT_HOME` containing only the signed-in account selection; the credential itself is resolved by the runtime from the system keychain or an existing `gh` CLI login. Each call then uses an isolated transient session with repository instructions, skills, Copilot memory, built-in tools, and the cross-session store disabled. This prevents the memory integration from recursively retaining its own extraction calls.

For automation, the Copilot SDK also accepts `COPILOT_GITHUB_TOKEN`, `GH_TOKEN`, or `GITHUB_TOKEN`. With one of those set, Copilot CLI never has to have been run on the host, so containers and CI images work with no `~/.copilot` at all. GitHub Actions and server-to-server deployments must have the appropriate Copilot organization policy and token permissions.

**Important notes:**
- Usage counts against the authenticated account or organization's Copilot allowance and AI Credits.
- `HINDSIGHT_API_LLM_BASE_URL` optionally points to an existing headless Copilot runtime, such as `http://127.0.0.1:4321`; it is not an LLM-provider endpoint for this provider.
- GitHub-hosted Copilot sessions do not expose temperature or maximum-output-token controls through the SDK, so those Hindsight settings are not applied.
- Embeddings and reranking continue to use Hindsight's separately configured providers; their local defaults require no API key.

</ProviderSetup>

### ChatGPT Setup (Sign in with ChatGPT)

The `chatgpt` provider runs Hindsight's LLM calls on your ChatGPT plan through
OpenAI's documented [Sign in with ChatGPT flow for open-source apps](https://developers.openai.com/siwc/token-sharing-open-source).
Hindsight registers itself as its own OAuth client on first sign-in, and every call goes to the public
`https://api.openai.com/v1/responses` endpoint with your OAuth access token. It does not use an API key.

<ProviderSetup>

How it differs from `openai-codex`: that provider reuses the Codex CLI's sign-in and calls ChatGPT's private
`chatgpt.com/backend-api/codex` endpoint. `chatgpt` uses the supported route and keeps its own
credentials, so it never shares or rotates the Codex CLI's tokens.

**Prerequisites:**
- A ChatGPT plan that allows plan usage in third-party apps
- A browser on the machine where you run the login

**Setup on a machine with a browser (for example a laptop):**

1. **Sign in:**
   ```bash
   hindsight-admin chatgpt login
   ```
   This opens your browser and waits for the callback on `http://127.0.0.1:1455/auth/callback`
   (`--port` changes the port; `--no-browser` prints the URL instead). Approve the request, including
   use of your ChatGPT plan. The command validates the ID token and the granted scopes, then writes
   `~/.hindsight/chatgpt/credentials.json` (mode `0600`) next to this host's `host_id`.
   If you declined plan usage, run `login --enable-plan-usage` to be asked again.

2. **Configure Hindsight:**
   ```bash
   export HINDSIGHT_API_LLM_PROVIDER=chatgpt
   # export HINDSIGHT_API_LLM_MODEL=gpt-6-luna       # the default
   # export HINDSIGHT_API_LLM_REASONING_EFFORT=medium  # sent as reasoning.effort
   ```

3. **Check the stored session** (prints account, client id, scopes and expiry, never token values):
   ```bash
   hindsight-admin chatgpt status
   ```

**Self-hosted server or VM (no browser):** the `127.0.0.1` callback reaches the machine running the
browser, so sign in on your laptop and move the credential file to the server.

1. On the laptop: run `login` as above.
2. Copy the file over SSH and install it on the server with `login --from-file`, as the user that runs Hindsight (add
   `--home <dir>` before `login` if the server sets `HINDSIGHT_API_LLM_CHATGPT_HOME`).
   `--from-file` keeps the server's own `host_id` (creating one on first use) instead of the laptop's:
   ```bash
   scp ~/.hindsight/chatgpt/credentials.json server:/tmp/chatgpt.json
   ssh server 'hindsight-admin chatgpt login --from-file /tmp/chatgpt.json && rm /tmp/chatgpt.json'
   ```
3. On the laptop, stop using that copy without revoking it:
   ```bash
   hindsight-admin chatgpt logout --local-only
   ```
   Refresh tokens rotate, so after the copy only the server may use and refresh this session. A plain
   `logout` would revoke it and end the server's session too. `--local-only` clears the laptop's
   tokens but keeps its client registration for a later `login`. `--from-file` refuses to replace a
   different account's registration on the server unless you pass `--force`.

The server then owns refreshes. Sign in again on the laptop later if you also want Hindsight there.

**Important notes:**
- Access tokens last one hour and are refreshed automatically (five minutes before expiry, and once on
  an HTTP 401). Refresh tokens rotate; refreshes take a file lock and re-read the file first, so
  several Hindsight processes can share one credential directory.
- When the refresh token is no longer valid, calls fail with the `login` command to run.
- On ChatGPT Plus, the five-hour usage limit is shared with every other app that uses your plan,
  including Codex. When the limit is reached, Hindsight defers retain and consolidation work and
  retries it 30 minutes later instead of failing it. Review usage and per-app limits at
  [ChatGPT Settings → Usage](https://chatgpt.com/settings/usage).
- The route is a preview: Hindsight sends `store: false` and `stream: true`, omits fields it rejects
  (`temperature`, `max_output_tokens`, `user`, and others), and sends system prompts as developer
  messages.
- `logout` revokes the session and clears local tokens but keeps the client registration and host id
  for the next `login`. `logout --local-only` clears the tokens without revoking.
- `HINDSIGHT_API_LLM_CHATGPT_HOME` relocates the credential directory. Use one directory per
  ChatGPT account. The directory must be writable, because each refresh writes the rotated token
  back; in a container, mount a writable volume there. If a write fails, the process keeps the new
  tokens in memory, but other processes and restarts will not see them.

</ProviderSetup>

#### Isolating Codex auth for long-running services

By default Hindsight reads Codex credentials from `~/.codex/auth.json` — the
same file the `@openai/codex` CLI, editor plugins, and other agent runtimes use.
This is convenient for local development but can cause a subtle failure mode when
Hindsight runs as a **long-lived service** (systemd unit, container, background
daemon) alongside another Codex process:

- Codex refresh tokens are single-use and rotate on refresh.
- If another process refreshes the shared token, Hindsight's long-running
  process is left holding a stale refresh token.
- Recall and `/health` keep working (the database and API are fine), but
  `/reflect` fails with an error such as:
  ```text
  Codex refresh_token is permanently invalid (error.code=refresh_token_reused).
  Run 'codex auth login' to re-authenticate.
  ```

To avoid this, give the Hindsight service its **own dedicated Codex auth home**
via the `CODEX_HOME` environment variable. Hindsight honors `CODEX_HOME` exactly
like the `@openai/codex` CLI: when set, it reads `$CODEX_HOME/auth.json` instead
of `~/.codex/auth.json`.

```bash
# Dedicated credentials directory for the Hindsight service
export CODEX_HOME=/var/lib/hindsight/codex

# One-time login into that isolated home (opens a browser / device-code flow)
codex auth login   # writes $CODEX_HOME/auth.json

export HINDSIGHT_API_LLM_PROVIDER=openai-codex
hindsight-api
```

For a systemd unit, set it in the service definition so it never shares auth
with an interactive Codex session:

```ini
[Service]
Environment=CODEX_HOME=/var/lib/hindsight/codex
```

After a fresh login into the dedicated home and restarting only the Hindsight
service, `/reflect` uses its own token that other Codex processes will not
rotate out from under it.

`CODEX_HOME` is also honored by the `openai-codex` embeddings provider.

#### Two Codex profiles in one process

`CODEX_HOME` is process-wide, so every Codex provider a Hindsight process builds
resolves the same `auth.json`. To run more than one independently authorized
ChatGPT account — for example, to fail over when the preferred account hits its
usage limit — give each one its own credentials directory with
`HINDSIGHT_API_LLM_CODEX_HOME` (primary) and `HINDSIGHT_API_LLM_<n>_CODEX_HOME`
(indexed [multi-LLM chain](./configuration#multi-llm-strategies-failover--round-robin)
members). Each falls back to `CODEX_HOME`, then `~/.codex`, when unset.

```bash
# Two profiles, logged in separately
CODEX_HOME=/var/lib/hindsight/codex-a codex auth login
CODEX_HOME=/var/lib/hindsight/codex-b codex auth login

export HINDSIGHT_API_LLM_PROVIDER=openai-codex
export HINDSIGHT_API_LLM_CODEX_HOME=/var/lib/hindsight/codex-a
export HINDSIGHT_API_LLM_1_PROVIDER=openai-codex
export HINDSIGHT_API_LLM_1_CODEX_HOME=/var/lib/hindsight/codex-b
export HINDSIGHT_API_LLM_STRATEGY='{"mode": "failover"}'
```

Token refresh is coordinated per auth-file path, so the two profiles refresh
independently and never overwrite each other's tokens. Failover is the generic
multi-LLM behaviour: a member is tried after the previous one has exhausted its
own retries and raised — there is no separate quota classifier or cooldown, so a
rate-limited primary is re-tried (and fails) at the head of each request before
the fallback serves it.

</ProviderSetup>

### Meta Model API Setup

[Meta Model API](https://ai.developer.meta.com) serves the Muse Spark models over an OpenAI-compatible endpoint.

<ProviderSetup>

Get a key from the Model API dashboard, then:

```bash
export HINDSIGHT_API_LLM_PROVIDER=meta
export HINDSIGHT_API_LLM_API_KEY=your-meta-model-api-key
export HINDSIGHT_API_LLM_MODEL=muse-spark-1.3
```

The base URL defaults to `https://api.meta.ai/v1`. Available models are
`muse-spark-1.3` (recommended), `muse-spark-1.2`, `muse-spark-1.1`, and the
discounted `-contributor` variants of 1.3 and 1.2, which permit training on your
prompts and completions. All share a 1,048,576-token context window.

#### Required knobs

Muse Spark **always reasons** before it replies. That single property drives every
setting below, so treat these as required rather than optional tuning:

| Variable | Set it to | Why |
|----------|-----------|-----|
| `HINDSIGHT_API_REFLECT_LLM_TIMEOUT` | `300` | Reflect's default is 30s. Muse Spark's final synthesis exceeds that, and the call fails after its retries rather than degrading — reflect returns nothing. |
| `HINDSIGHT_API_LLM_TIMEOUT` | `300` | The global deadline (default 120s) covers retain and consolidation, which are slower here than on a non-reasoning model. |
| `HINDSIGHT_API_LLM_REASONING_EFFORT` | unset, or `minimal`/`low`/`medium`/`high`/`xhigh` | `none` is rejected with `HTTP 400`. Leave it unset to let the model choose its own depth. |
| `HINDSIGHT_API_RETAIN_MAX_COMPLETION_TOKENS` | leave at the `64000` default | Reasoning tokens are billed against the **output** budget. Lower this too far and a reply comes back with no content at all. |

#### Good to know

- **Prompt caching is automatic.** There is no key, flag, or breakpoint to set — Meta
  reuses a matching prompt prefix on its own, so the capability table below lists no
  explicit prompt-caching support even though the benefit applies.
- **No batch API and no embeddings endpoint.** Embeddings continue to come from
  whichever `HINDSIGHT_API_EMBEDDINGS_PROVIDER` you configure.
- **Recursive JSON schemas are rejected** with `HTTP 400`. No Hindsight code path
  sends one, so this only matters if you add a self-referencing response model.
- **Expect slower calls.** A trivial prompt can spend more tokens reasoning than it
  returns as output.

</ProviderSetup>

### Cursor Setup (Cursor subscription)

Serve Hindsight's extraction, consolidation and reflection calls from a **Cursor
subscription**, by driving the `cursor-agent` CLI in its headless print mode. No API key
and no second per-token billing relationship.

<ProviderSetup>

This is the opposite direction from the [Cursor integration](/sdks/integrations/cursor),
which makes Cursor a *client* of Hindsight. Here Cursor is the model backend Hindsight calls.

**Prerequisites:**
- An active Cursor subscription (a free plan works, but only with `auto` — see below)
- `cursor-agent` installed and signed in under the same OS user that runs Hindsight

**Setup Steps:**

1. **Install the CLI:**
   ```bash
   curl https://cursor.com/install -fsS | bash
   ```

2. **Log in:**
   ```bash
   cursor-agent login
   ```

3. **Verify:**
   ```bash
   cursor-agent --version
   cursor-agent --list-models
   ```

4. **Configure Hindsight:**
   ```bash
   export HINDSIGHT_API_LLM_PROVIDER=cursor
   export HINDSIGHT_API_LLM_MODEL=auto
   # An agent CLI turn takes 15-30s, well past the 30s reflect default.
   export HINDSIGHT_API_LLM_TIMEOUT=300
   export HINDSIGHT_API_REFLECT_LLM_TIMEOUT=180
   # No API key needed. To authenticate with a key instead:
   # export HINDSIGHT_API_LLM_API_KEY=...   # or CURSOR_API_KEY
   ```

**Important notes:**

- **Raise the timeouts.** Each call spawns a `cursor-agent` turn, which takes 15-30s
  against `auto` — slower than a chat-completions request and past the 30s
  `HINDSIGHT_API_REFLECT_LLM_TIMEOUT` default. Left at the default, reflect spends its
  first iteration on timeout retries before recovering.
- **Structured output is a prompt-level emulation.** The CLI exposes no
  `response_format`, JSON-schema or temperature flag — only
  `--output-format text|json|stream-json`, which describes the envelope. Hindsight puts
  the schema in the prompt and parses the model's JSON back out, retrying on a parse
  failure. That is less reliable than a native schema, so prefer a strong named model
  over `auto` for reflect, the operation that leans hardest on it.
- **Free plans are limited to `auto`.** A named `--model` returns
  `Named models unavailable Free plans can only use Auto`. Paid plans can use any id from
  `cursor-agent --list-models`.
- **The agent's own tools are turned off.** `cursor-agent` is an agent, not a completions
  endpoint: it ships Shell, Read, Write, Delete, web fetch and more, and `--mode ask` is
  *not* a tool switch — a headless run in ask mode will still read files out of its
  working directory. Hindsight therefore runs the CLI in an empty scratch workspace, with
  its own `CURSOR_CONFIG_DIR` (so it never sees your `~/.cursor` config, hooks or session
  history), and writes a `cli-config.json` there that denies every tool by name. That is
  the equivalent of the `tools=[]` the `claude-code` provider passes its SDK, and it
  matters because retain prompts are built from whatever text you store in Hindsight.
- Usage counts against your Cursor subscription.
- Reasoning effort is not supported — the CLI has no such flag, and Hindsight warns once
  at startup if `HINDSIGHT_API_LLM_REASONING_EFFORT` is set.
- Embeddings and reranking continue to use Hindsight's separately configured providers.

</ProviderSetup>

### SuperGrok Subscription Setup (device-code OAuth)

Serve LLM calls from a **SuperGrok subscription** (device-code OAuth) — no API
key. For API-key access to `api.x.ai`, use `provider: openai` with
`HINDSIGHT_API_LLM_BASE_URL=https://api.x.ai/v1`; **this provider is the
subscription lane**, the same category as `openai-codex` (ChatGPT subscription)
and `claude-code` (Claude subscription). Both routes reach the same published
endpoint, so the credential is the whole difference: a flat-rate consumer
subscription authorized once in a browser, instead of a per-token metered key.

<ProviderSetup>

Authentication is xAI's own OIDC issuer at `https://auth.x.ai` using the RFC
8628 device-code flow, with the public OAuth client id published in xAI's
Apache-2.0 Grok CLI sources. Hindsight keeps its own credential file and never
reads or writes the Grok CLI's `~/.grok/auth.json`.

:::note Subscription entitlement

xAI may restrict `api.x.ai` access by SuperGrok subscription tier: an OAuth
grant can be valid and still be refused with HTTP 403. Hindsight reports that
as a distinct entitlement error naming the cause rather than as a credential
failure, and it neither re-tries nor discards the token. If you hit it, verify
the account tier or use an API-key provider instead.

Usage counts against your SuperGrok subscription limits. When the account's
spending limit stops a call, Hindsight raises a distinct quota error and leaves
the credential alone.

:::

**Prerequisites:**
- An active SuperGrok subscription
- A browser on the machine you run the login from (the device-code flow needs
  an interactive approval; the running service never performs one)

**Setup steps:**

1. **Log in once, on the host that will own the credential:**
   ```bash
   python -m hindsight_api.engine.providers.xai_oauth_auth login
   ```
   The command prints a verification URL and a user code, waits for approval,
   then writes `~/.hindsight/xai_oauth.json` with owner-only permissions.

2. **Configure Hindsight:**
   ```bash
   export HINDSIGHT_API_LLM_PROVIDER=xai-oauth
   # export HINDSIGHT_API_LLM_MODEL=grok-4.5   # defaults to grok-4.5
   # No API key needed
   ```

3. **Start Hindsight:**
   ```bash
   hindsight-api
   ```

**Important notes:**
- The access token is refreshed automatically: proactively 60 seconds before
  expiry (or before the configured request timeout, whichever is longer), and
  once reactively on an HTTP 401. Several configured lanes share one credential
  file safely — the refresh takes an advisory lock and re-reads the file under
  it, so siblings do not each refresh.
- A running service **never** starts the device-code flow. When only a login can
  restore service, calls fail with the exact command to run.
- Unlike reaching `api.x.ai` through `provider: openai`, this provider sends the
  member's configured `reasoning_effort`, so that setting takes effect here.
  The one value not forwarded is `none`: xAI rejects it outright (HTTP 400),
  so this lane expresses it the way the API expects — by omitting the field.
- Only non-streaming calls are implemented. Streaming responses omit
  `prompt_tokens_details`, so cached-token accounting would read low.

**Optional environment overrides:**

| Variable | Purpose | Default |
|---|---|---|
| `HINDSIGHT_API_XAI_OAUTH_BASE_URL` | Point at a different upstream. Takes precedence over `HINDSIGHT_API_LLM_BASE_URL`. | `https://api.x.ai/v1` |
| `HINDSIGHT_API_XAI_OAUTH_TOKEN_PATH` | Relocate the credential store. Both the read and the write follow it. | `~/.hindsight/xai_oauth.json` |
| `HINDSIGHT_API_XAI_OAUTH_CLIENT_ID` | Override the OAuth client id used for login and refresh. | xAI's published public client id |
| `HINDSIGHT_API_XAI_OAUTH_SCOPE` | Override the scope string requested at login. | `openid profile email offline_access grok-cli:access api:access` |
| `HINDSIGHT_API_XAI_OAUTH_REFRESH_SKEW_SECONDS` | Refresh this many seconds before expiry. Widen it for deployments that touch the provider rarely. | `60` |
| `HINDSIGHT_API_XAI_OAUTH_REFRESH_TIMEOUT_SECONDS` | Per-request timeout for discovery, login and refresh calls. | `20` |

#### Deployment note

The credential is a host-local file, and only the interactive login can create
it. A containerized engine therefore needs the store mounted from a host where
the login was run (or the login run inside the container once, interactively)
and `HINDSIGHT_API_XAI_OAUTH_TOKEN_PATH` pointed at it. The mount must be
**writable**: unlike the Grok CLI's own file, this store is where Hindsight
persists each rotated token, so a read-only mount degrades to failing once the
current token expires.

xAI issues a **new refresh token on every refresh** and retires the one it
replaces. Replicas must therefore share the one credential file rather than
each starting from its own copy of a single login's output: a copy stops
working as soon as another replica refreshes, and the login has to be repeated.
A single shared writable volume is the supported shape; if you cannot provide
one, run one replica on this provider and give the others an API-key lane.

</ProviderSetup>

### Azure OpenAI Setup

Azure OpenAI is reached through the **`openai`** provider — there is no `azure`
provider, and setting one fails at startup with
`Invalid LLM provider: azure`.

<ProviderSetup>

The one thing that trips people up is the base URL. Azure does not serve the
OpenAI API at the resource root, so the endpoint shown in the Azure portal is
not usable on its own:

| `HINDSIGHT_API_LLM_BASE_URL` | Result |
|---|---|
| `https://<resource>.openai.azure.com` | `404 Resource not found` |
| `https://<resource>.openai.azure.com/openai/deployments/<deployment>` | `404 Resource not found` (no `api-version`) |
| `https://<resource>.openai.azure.com/openai/v1` | works |
| `https://<resource>.openai.azure.com/openai/deployments/<deployment>?api-version=<version>` | works |

**Recommended — the v1 surface:**

```bash
export HINDSIGHT_API_LLM_PROVIDER=openai
export HINDSIGHT_API_LLM_API_KEY=<azure-openai-resource-key>
export HINDSIGHT_API_LLM_MODEL=<deployment-name>
export HINDSIGHT_API_LLM_BASE_URL=https://<resource>.openai.azure.com/openai/v1
```

**Or the deployment-scoped form.** Keep the `api-version` query string — Hindsight
parses it out of the base URL and passes it to the SDK:

```bash
export HINDSIGHT_API_LLM_BASE_URL=https://<resource>.openai.azure.com/openai/deployments/<deployment>?api-version=2025-01-01-preview
```

**Important notes:**
- `HINDSIGHT_API_LLM_MODEL` is your **deployment name**, not the model name. A
  `gpt-4o` deployed as `my-gpt4o` is configured as `my-gpt4o`.
- The key is the Azure OpenAI **resource** key (`az cognitiveservices account
  keys list -n <resource> -g <group>`). An API Management subscription key is a
  different credential: with APIM in front, the base URL must be the APIM route
  and APIM has to forward the `api-key` header. Test against the Azure endpoint
  directly first to isolate which layer is failing.
- Gateways and proxies must preserve the same path shape (`/openai/v1` or
  `/openai/deployments/...?api-version=`).
- Azure OpenAI accepts `prompt_cache_key` on GPT deployments (it improves cache
  routing on GPT-5.6 and later), but the same `*.openai.azure.com` endpoint also
  serves non-OpenAI Foundry models (DeepSeek, Llama, Mistral) that reject it with
  `unrecognized_request_argument`. The host alone can't tell the two apart, so
  [`HINDSIGHT_API_LLM_CACHE_AFFINITY`](./configuration#llm-provider) resolves
  `auto` to `none` for Azure hosts. If your deployment serves an OpenAI model,
  set it explicitly to `openai_prompt_cache_key`.

</ProviderSetup>

:::tip AWS Bedrock application inference profiles

If your org's Service Control Policy denies `bedrock:InvokeModel` on the bare model id once an [application inference profile](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-profiles-support.html) exists, keep `..._MODEL` as is and add the profile ARN separately:

```bash

# Stays a recognizable model id: this is what picks the request format
export HINDSIGHT_API_EMBEDDINGS_LITELLM_SDK_MODEL=bedrock/amazon.titan-embed-text-v2:0

```

The two are separate because Bedrock's embedding request and response formats differ per model family (Titan, Cohere, TwelveLabs, Nova), and the family is read off the model id. A profile ARN is opaque and account-scoped, so it can't be used for that.

Chat models don't need this: set `HINDSIGHT_API_LLM_MODEL=bedrock/converse/<arn>`, since the Converse API takes one format for every model.

:::

## Cross-Encoder (Reranker)

Orders recall's candidates by relevance to the query. The default, [`hindsight-ai/hs-rerank-1`](https://huggingface.co/hindsight-ai/hs-rerank-1) (multilingual, 114M parameters), runs in the API process with no setup. Pick a provider with `HINDSIGHT_API_RERANKER_PROVIDER`; every option is in [Configuration › Reranker](./configuration#reranker). With a [decision model](#decision-model) set up for recall, the decision model ranks instead.

<ModelProviderSearch only="reranker" />

### Hindsight Inference {#reranker-hindsight}

[Hindsight Inference](https://inference.hindsight.vectorize.io) serves `hs-rerank-1`, a cross-encoder built for agent memory: eight languages, queries and documents up to 8,192 tokens.

<ProviderSetup>

Sign in once with [`hindsight-admin cloud login`](./admin-cli#cloud), then:

```bash
export HINDSIGHT_API_RERANKER_PROVIDER=hindsight
```

On a server where you can't sign in, set the key instead: `HINDSIGHT_API_RERANKER_HINDSIGHT_API_KEY`. It wins over the saved sign-in.

The weights are open: [`hindsight-ai/hs-rerank-1`](https://huggingface.co/hindsight-ai/hs-rerank-1) (114M, MIT) also runs on your own machine: see [Local](#reranker-local).

</ProviderSetup>

### Local {#reranker-local}

SentenceTransformers CrossEncoder in the API process: no key, no network once the model is downloaded. The default model is [`hindsight-ai/hs-rerank-1`](https://huggingface.co/hindsight-ai/hs-rerank-1), our open reranker built for agent memory.

<ProviderSetup>

`hs-rerank-1` has 114M parameters (MIT), works in eight languages and reads inputs up to 8,192 tokens. Most of its weights are the vocabulary table, so each pass runs a 15M-parameter transformer, and it's fast on CPU.

```bash
export HINDSIGHT_API_RERANKER_PROVIDER=local
export HINDSIGHT_API_RERANKER_LOCAL_MODEL=hindsight-ai/hs-rerank-1
```

It downloads from Hugging Face on first start. Any other cross-encoder works the same way:

| Model | Use |
|---|---|
| `hindsight-ai/hs-rerank-1` | Default. Built for agent memory, 8 languages, 8,192-token inputs |
| `cross-encoder/ms-marco-MiniLM-L-6-v2` | Fast, English (the default before hs-rerank-1) |
| `cross-encoder/ms-marco-MiniLM-L-12-v2` | More accurate, English |
| `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1` | Multilingual |

To serve it on its own machine or a GPU instead, run it on [Text Embeddings Inference](https://github.com/huggingface/text-embeddings-inference) (the CPU image uses the model's int8 ONNX export) and point the `tei` provider at it:

```bash
docker run -p 8080:80 ghcr.io/huggingface/text-embeddings-inference:cpu-1.9.3 \
  --model-id hindsight-ai/hs-rerank-1 --auto-truncate

export HINDSIGHT_API_RERANKER_PROVIDER=tei
export HINDSIGHT_API_RERANKER_TEI_URL=http://localhost:8080
```

For a GPU, use the GPU image: `89-1.9.3` for L4 and other Ada GPUs, `1.9.3` for A100 and H100, with `--gpus all`.

</ProviderSetup>

### TypeSafe (deprecated) {#reranker-typesafe}

Deprecated: set up the [decision model](#decision-model) with the `typesafe` provider instead. Recall uses it in place of the reranker, and consolidation, reflect and knowledge pages get it too.

<ProviderSetup>

TypeSafe isn't a `/rerank` endpoint: it answers typed questions about a state. Hindsight makes the candidates the options of one choice question, and the probabilities it returns are the ranking. A pool that fits the 250-option limit and the token budget is ranked in one call; a larger one is split into groups whose top candidates go on to a final round. `HINDSIGHT_API_RERANKER_TYPESAFE_PRUNE_CANDIDATES=true` adds a second question that cuts the list where relevance ends (see [Configuration](./configuration#typesafe)). Its scores are rank positions, not relevance, so recall publishes no `scores.reranker` and rejects `min_scores.reranker` with HTTP 400.

</ProviderSetup>

## Decision Model

Answers short typed questions (yes or no, pick one of these, how likely is this) in well under a second, so Hindsight can skip an LLM call for a judgment that needs no writing. Optional: with none set up (`HINDSIGHT_API_DECISION_MODEL_PROVIDER=none`, the default), every operation keeps its LLM-only path. See [Decision Models](./decision-models) for what each operation does with it, and [Configuration](./configuration#decision-model) for every option, including per-operation overrides.

<ModelProviderSearch only="decision" />

Reflect and knowledge-page refresh support only `hindsight` and `typesafe` for now. With another provider they keep their LLM-only path and log a warning, while recall and consolidation still use it. To pair another provider with `hindsight` or `typesafe` for reflect, override the reflect provider (see [OpenAI Decisions](#decision-openai)).

When the endpoint serves another model than the provider's default, also set `HINDSIGHT_API_DECISION_MODEL_MODEL` and `HINDSIGHT_API_DECISION_MODEL_TOKENIZER`, and set `HINDSIGHT_API_DECISION_MODEL_MAX_REQUEST_TOKENS` to that model's context window less a margin.
